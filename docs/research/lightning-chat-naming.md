# Lightning chat naming in stock Codex clients

Investigated 2026-09-23 for [#41](https://github.com/kreuzhofer/nebius-tofa-cli/issues/41), following [the agreed specification #36](https://github.com/kreuzhofer/nebius-tofa-cli/issues/36). Exact candidate: `nvidia/Nemotron-3_5-Lightning`. This is an independent naming investigation; it does not add a main-model or Guardian candidate to [#28](https://github.com/kreuzhofer/nebius-tofa-cli/issues/28).

## Conclusion

**No verified, supported route through the existing launcher selects Lightning for automatic titles independently of the main and Guardian roles.** Both inspected clients generate automatic titles, but their selection rules differ. CLI 0.155.1's interactive TUI uses the current conversation model for a custom provider. The installed desktop requests a fixed auxiliary model and permits provider-catalog fallback. Neither inspected title-generation path reads a dedicated title-model setting. These conclusions are bounded to the versions and source paths below; they do not claim that every Codex version lacks such a feature. [CLI selection][cli-title], [desktop evidence](#installed-desktop-evidence), [configuration schema][cli-config].

Desktop has a concrete **source-only feasibility lead**: an authoritative catalog could make Lightning the provider default while main and Guardian remain explicitly selected. That is a generic catalog fallback with effects on other auxiliary tasks, not a title-specific configuration contract. The current launcher does not express a naming role or carry Lightning's verified metadata, and no desktop runtime experiment established this arrangement. Investigate this bounded lead before changing request adaptation. [Catalog fallback][desktop-manager], [launcher catalog][launcher-metadata].

No paid inference, new client session, desktop patch, model-ID rewrite, settings edit, credential access, or private-conversation inspection was performed for this investigation. Consequently Lightning's title quality, latency, cost, Responses compatibility, and successful independent routing remain **unqualified**. The existing desktop Kimi title failure remains relevant to [#33](https://github.com/kreuzhofer/nebius-tofa-cli/issues/33); that issue was open with no comments when inspected, so this report reuses the prior failure evidence rather than claiming a completed fix. [Prior sanitized experiment][prior-desktop].

## CLI: automatic naming exists, but custom-provider naming follows main

The interactive TUI starts a hidden title thread. It selects `gpt-5.6-luna` only when all three conditions hold: provider ID is `openai`, a ChatGPT account is present, and the catalog contains that model. Otherwise it copies `chat_widget.current_model()`. It copies the active provider ID into the temporary thread. Thus selecting Lightning as the main model would also select it for naming, but would violate this investigation's requirement to preserve the main role. Changing catalog priority alone cannot override this explicit custom-provider title selection. [Pinned `generate_thread_title`][cli-title].

Upstream tests drive automatic generation through the embedded app-server and assert the generated title is persisted; separate tests cover an editable `/rename` suggestion and preservation of an existing manual title. These are inspected upstream tests, **not tests executed against Token Factory here**. The conclusion concerns interactive TUI naming; `codex exec` was not demonstrated to generate titles, and its absence is not necessary to the blocker. [Pinned title tests][cli-title-tests].

The CLI title contract is a JSON object containing only a required `title` string, length 1–36, with `additionalProperties: false`. The helper starts an ephemeral thread, explicitly disables shell, unified execution, code mode, image viewing, apps, plugins and other tools, reads effective MCP configuration and disables those servers, and supplies empty dynamic tools, selected capabilities, environments and workspace roots. It preserves an existing custom permission profile or requires read-only permissions; approval policy is `never`. Its structured request is bounded to 30 seconds and 8 KiB of response text. This differs materially from the desktop helper. The exact serialized tool list was not captured here. [Title schema][cli-title], [temporary structured requests][cli-structured].

The inspected CLI configuration schema exposes no separate chat-title model field. The documented `model`, `model_provider`, and `model_catalog_json` concern ordinary model/provider/catalog selection; `tui.terminal_title` controls terminal window/tab display items, not generated conversation names. Do not invent `title_model`, confuse terminal-title presentation with inference, or use Guardian selection as a naming switch. [Pinned configuration schema][cli-config], [official configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference).

## Installed desktop evidence

These locators refer to the installed archive identified above. They can be reproduced by reading the named archive entries without launching the app or opening its state. String/function locators are preferable to unstable minified line numbers. Both inspected entries matched the previously extracted local copies byte-for-byte.

| Archive member | SHA-256 | Relevant locators |
| --- | --- | --- |
| `.vite/build/src-C3YaUE83.js` | `14c8c23e8b8dfa874d3fb5a50d54fb28eccf55fb83232c3ab29cb7c0ef0a0472` | `WN`, `ece`, `X9`, `z8`, `bN`, `G9`, `rce`, `Bne` |
| `.vite/build/main-DUHZj4_w.js` | `9e8a3bd79c817064f28693ca26aa1378895e07ab2108c78c42d0ea20dac9d66e` | `ThreadMetadataGenerationService`, class `I5`, method `generateTitle` |

The title call chain is `I5.generateTitle → ece → X9 → z8 → bN`. `ece` marks the operation `thread_title`; `X9` passes fixed `WN = gpt-5.6-luna` and effort `low`; `z8` creates an ephemeral thread with `modelProvider: null` and, by default, `allowProviderModelFallback: true`. The ordinary `generateTitle` service call does not supply a source thread, so this path starts a fresh thread. `bN` then sends the prompt and `outputSchema` through `startTurn`, with `model: null`, inheriting the temporary thread's chosen model. The title service's arguments contain no title-model override. [Installed archive locators above](#installed-desktop-evidence).

`modelProvider: null` leaves provider resolution to the app-server configuration. The bundled engine's `ThreadStartParams` labels `allowProviderModelFallback` **experimental** and describes fallback for a provider with an authoritative static catalog. Its static model manager preserves a requested model present in the available catalog; otherwise, with fallback enabled, it selects the catalog default. The ordinary manager preserves an explicitly requested model. This explains why an auxiliary request can retain the native ID without a suitable authoritative catalog and why the previous launcher-catalog experiment selected Kimi instead. [Thread-start contract][desktop-thread], [model-manager implementations][desktop-manager], [observed fallback][prior-desktop].

### The actual title protocol, and what remains unknown

| Concern | Confirmed evidence |
| --- | --- |
| Operation identity | `thread_title` as temporary thread source and turn trigger; this positively identifies title generation. A request for an auxiliary model alone does not. [Installed `ece`, `X9`, `bN`](#installed-desktop-evidence). |
| Output | The desktop requires **both** `title` (string, 1–36 characters) and `description` (nonempty string). It generates the schema from `G9`, parses JSON, validates against `G9`, normalizes the title, and normalizes/truncates the description to 100 characters. This is not the CLI's title-only schema. [Installed `G9`, `ece`, `Y9`, `xN`, `Bne`](#installed-desktop-evidence). |
| Wire representation | The engine builds Responses `text.format` with `type: json_schema`, `name: codex_output_schema`, and the supplied schema. Ordinary title turns use `strict: true`; the non-strict exception is for basic Guardian sessions. [Engine text formatting][desktop-text], [prompt construction][desktop-turn]. |
| Tools | Title generation uses the normal turn's model-visible tool specifications. Its desktop helper disables fanout, hooks, multi-agent, plugins, shell snapshots, tool suggestions and web search; it disables its `codex_app` MCP server. It does **not** explicitly disable shell, unified execution or code mode. Optional read-only app allowlists may enable named app tools. Read-only permissions and `approvalPolicy: never` do not mean an empty tool list. [Installed `X9`, `rce`, `z8`](#installed-desktop-evidence), [engine tool routing][desktop-turn]. |
| Historical request | The prior live experiment identified `ThreadMetadataGenerationService` and an adapter rejection of nonempty tools plus JSON schema. It did not retain the title's exact tool names/count, exact wire schema or app allowlist. Those details cannot be reconstructed as observed facts from the error. [Sanitized prior evidence][prior-desktop]. |
| Transport and bounds | Prior desktop provider traffic used streaming HTTP Responses. This helper waits up to 30 seconds, interrupts on timeout/cancellation where supported, and unsubscribes its temporary thread. The source inspection is not a fresh wire capture. [Prior desktop contract][prior-desktop], [installed `V9`, `z8`, `bN`](#installed-desktop-evidence). |

The existing adapter rejects the historical Kimi shape **before upstream inference**. Its exception requires the exact recognized Guardian schema, explicit non-strict formatting, automatic tool choice, and exactly the permitted Guardian tools. A strict title/description schema is outside that exception. Absent/empty tools or `tool_choice: none` take separate pass-through branches; those branches do not establish that the desktop actually sent an empty tool list. [Pinned `adaptApprovalReview`][adapter].

The guard is specifically for `moonshotai/Kimi-K3`: other model IDs pass this function unchanged. Therefore the Kimi failure neither proves Lightning fails nor establishes that Lightning accepts this combination. Removing the guard or applying the Guardian schema-to-prompt transformation to titles would change product behavior and abandon the demonstrated narrow contract; neither was done. [Adapter model gate and validation][adapter].

## Configuration versus source-only feasibility

| Status | Finding and consequence |
| --- | --- |
| Confirmed configuration | Codex supports a custom provider and a startup `model_catalog_json`. This does not itself promise role-specific title routing. [Configuration reference](https://learn.chatgpt.com/docs/config-file/config-reference). |
| Confirmed CLI source | For the launcher custom provider, the title helper explicitly selects the current main model. No independent Lightning selection follows from a catalog default. [CLI title selector][cli-title]. |
| Confirmed desktop source | A fixed requested model plus static-provider fallback can choose the catalog default. There is no title-specific selector in the inspected service/helper arguments. [Installed helper](#installed-desktop-evidence), [engine fallback][desktop-manager]. |
| Observed fallback | The existing desktop Kimi experiment selected Kimi for title generation with the launcher catalog, then failed adapter validation. This is evidence of fallback, not deliberate Lightning routing. [Prior experiment][prior-desktop]. |
| Source-only candidate | Put Lightning first among eligible picker-visible catalog entries (lowest numeric priority), keep the main model explicitly selected, and preserve the explicit Guardian override. The static manager sorts priority, chooses the first visible entry as default, and uses it for unavailable auxiliary models. This is technically plausible, not runtime-proven. [Catalog ordering/default selection][desktop-manager], [default marking][desktop-models]. |
| Scope of that candidate | `X9` also generates descriptions and summaries; other ephemeral helpers use the same fallback mechanism. A global catalog default could route these requests too. It is not a naming-only switch, and an auxiliary inventory/regression check is required. [Installed `X9`, `tce`, `nce`, `wN`](#installed-desktop-evidence). |
| Existing launcher limitation | `prepareModelCatalog(model, guardian)` includes only the selected main role and a distinct Guardian when provided. It gives them priority 0 in that order and sets `auto_review_model_override` on main when applicable. Lightning is absent from the bundled candidate metadata. There is no naming-role argument or independently selected title catalog entry. [Catalog construction][launcher-metadata], [bundled snapshot][launcher-snapshot]. |

Do not advertise the catalog-default candidate as impossible, native title-model support, or a completed launcher capability. Adding accurate Lightning metadata and an explicit catalog-default/auxiliary policy would be new product work. The live catalog/price note in #41 is historical context only: this research did not refresh authenticated availability or current pricing and uses neither as compatibility evidence. [Issue #41](https://github.com/kreuzhofer/nebius-tofa-cli/issues/41), [launcher snapshot][launcher-snapshot].

## Narrow next work and bounded qualification

1. **Resolve the desktop catalog-default feasibility question separately from adapter changes.** In a version-pinned isolated desktop, use an accurately sourced catalog with explicit main and Guardian IDs and Lightning as the candidate default. Capture automatic title generation at the desktop-to-app-server boundary and the resulting local-provider boundary. Establish requested versus resolved model/provider IDs and enumerate all other auxiliary sources affected. Do not silently relabel `gpt-5.6-luna` as Lightning. If this cannot be exposed as an explicit, reviewable auxiliary policy, request an upstream title-role configuration contract. The lead comes from [the static fallback code][desktop-manager], not from an existing naming API.
2. **Keep the CLI follow-up separate.** It needs an upstream title-model/provider selector or a separately approved launcher-owned naming feature because its current custom-provider path explicitly selects main. Do not patch the installed client or treat changing main as independent naming. [CLI selector][cli-title].
3. **Reuse #33 for request-shape work.** First obtain a sanitized exact title request: tool types/names/namespaces, structured-output schema/strictness, reasoning and request-source metadata. Determine whether tool suppression can be supported specifically for title generation or whether Token Factory accepts the actual Lightning request. Preserve strict validation and existing Guardian behavior; do not expand its workaround. [Existing title failure][prior-desktop], [adapter contract][adapter].

Once a concrete route exists, the following is a **proposed** qualification budget, not an executed test or permission to make paid calls:

- Use a fresh owned desktop/Codex state directory, empty scratch workspace, synthetic conversations and dummy local credentials for the first boundary run. Preserve ordinary configuration and credential stores. At the highest available client boundary, verify actual automatic generation, exact selected main/Guardian IDs, `nvidia/Nemotron-3_5-Lightning` only in the intended auxiliary role, request source, and title persistence. A synthetic provider response qualifies routing/serialization only.
- Before live inference, refresh exact project catalog availability and provider Responses/tool/schema metadata, prices, and output limits. Use three synthetic naming cases (short task, ticket reference, non-English task), at most one initial title request plus one diagnostic retry per case, with a 30-second deadline per attempt, a proposed 256-output-token ceiling, a 4,096-input-token preflight ceiling per naming attempt and a proposed USD 0.10 title-only cap. If the actual desktop request exceeds a ceiling, stop and revise the explicit budget rather than truncate silently. Budget main/Guardian controls separately before running them.
- Retain sanitized local correlation IDs **and upstream request/response IDs**, requested/resolved/upstream model IDs, categorical tool/schema shape, HTTP/result status, displayed title and schema-validity result, elapsed wall time, reported input/output/cached usage, contemporaneous rates and calculated cost. If service usage or request IDs are absent, mark them unavailable rather than inventing exact cost or traceability.
- Check title usefulness against the synthetic request: relevant, nonempty, correct language, ticket retained where applicable, no invented action/result, within the actual client's schema and display limits. Check timeout, invalid output and refusal behavior. A JSON-valid response alone is insufficient.
- Verify main streaming/tool/continuation behavior and the configured Guardian route remain intact at request boundaries; detect all unexpected auxiliary traffic. Confirm state/credential preservation and owned-process cleanup. Report the exact client/model/provider combination and any unexecuted tests. Availability or a mocked response must not promote Lightning to a supported model.

These are proposed acceptance checks informed by the [two title contracts][cli-title] and [desktop evidence](#installed-desktop-evidence); no quality, speed, price advantage or model support is claimed.

## Checks and limits

Read-only checks performed: installed version commands and bundle metadata; SHA-256 of the installed archive and relevant JavaScript entries; byte equality of cached and installed JavaScript; public release-tag resolution; inspection of CLI title/configuration/tests, desktop helper and engine fallback/serialization source, launcher catalog and adapter; current official configuration documentation; existing sanitized desktop evidence and issue #33 status. No raw session traces, account identifiers, credentials, or review rationales were read or retained.

The coordinating agent ran `go test ./internal/tofa -run 'TestAdapter(MovesGuardianGuidanceAndPreservesRequest|RejectsUnsupportedKimiConstrainedTools|LeavesUnrelatedGenerationOptionsUnchanged)$' -count=1`. All three existing adapter tests passed after permitting their loopback test listeners; the initial sandbox-only attempt could not bind localhost. These tests check the existing adapter contract, not title routing or Lightning inference. Upstream Codex tests were inspected but not executed. No new runtime desktop/TUI title capture or paid qualification was performed because a supported current-launcher route was not established.
