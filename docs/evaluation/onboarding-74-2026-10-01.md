# First-use authentication before launch selection (#74)

Implementation: `6dcea2483b50efa7c6cd5e30b0a1ac997136cc36`.
Baseline: `df9f8055f229338a74a3c0f49fb559754c7ee08a`.
Issue: [#74](https://github.com/kreuzhofer/tofa-launcher/issues/74).

Fresh interactive launches now announce setup and reuse `auth login` before
selection. Setup distinguishes saving credentials locally from authenticating
against the selected project's catalog. It continues the original invocation
only after that check succeeds. Explicit main, Guardian, project, target and
client arguments survive onboarding. Invalid arguments and explicit desktop
platforms are rejected before credential entry.

A valid saved login skips onboarding. Missing saved keys, inaccessible vaults,
malformed configuration and interrupted credential state require explicit
recovery. They cannot trigger automatic replacement or plaintext fallback.
Cancellation/EOF at either credential prompt leaves no saved login. Non-TTY
launches remain noninteractive and include login guidance. Standalone `auth login`
retains its local-save-only contract; help, version, doctor and uninstall remain
outside launch onboarding.

## Reproduction and test-first evidence

The maintainer's original Windows observation was initially distinct from the
source observation. Both platforms now have executable evidence:

- The first macOS PTY regression, running the compiled CLI entry point with
  isolated state, failed waiting for `API key:` because `Choose an app` appeared
  first. After implementation it authenticates, selects an app and model, and
  starts the synthetic client in the same invocation.
- The unchanged baseline was cross-built and executed natively in Windows 11
  ARM64 UTM. It displayed the app picker without an API-key prompt; selecting
  Codex CLI returned `not logged in; run tofa auth login`. See the
  [baseline report](evidence/onboarding-74-2026-10-01/baseline-windows.json).
- Additional failing regressions covered explicit launches, argument validation,
  orphaned credential state and missing noninteractive login guidance before
  their fixes. The project prompt now treats a zero-byte read as EOF.

The permanent regression boundary is `scripts/picker_test.py`, using the compiled
`App.Run` entry point, real terminal input, a real child executable and a loopback
catalog. The production binary exposes no provider/vault fixture overrides.
Desktop coverage uses the existing executable desktop fixture and installed
bundled engine. Native Windows checks used ARM64 Python 3.13, pywinpty 3.0.5,
ConPTY and the existing limited `SabreTest` account.

## Validation and failures

- `go test -race -timeout 20m ./...`: passed, with the installed desktop engine
  enabled. The first full run found one stale help-text assertion; it was updated,
  checked individually, and the final full run passed.
- `go vet ./...` and `git diff --check`: passed.
- CLI PTY suite: 38 tests passed. Desktop terminal suite: 21 tests passed,
  including explicit first-use main/Guardian/project retention.
- All 18 Python test scripts completed successfully with their documented
  arguments and standard CI options. Expected platform/optional skips remain
  explicit. Native macOS candidate terminal tests (2) and installation lifecycle
  tests (4) passed.
- Windows ARM64 authentication/storage tests passed natively, including synthetic
  locked, denied, missing-entry and failed-write cases. Native macOS Keychain and
  Windows Credential Manager first-use/reuse checks also passed.

An additional, optional desktop evaluation run with the installed engine produced
14 failures with `client_error` after completed synthetic work. A representative
failure, `DesktopEvaluationTests.test_command_to_report_checks_tools_resume_approvals_and_preservation`,
was reproduced against the unchanged starting commit. This existing evaluation
failure is recorded separately from the passing standard checks and is not claimed
fixed by #74.

Harness failures were corrected explicitly: unittest discovery omitted the
standalone installer/terminal script arguments; a temporary macOS `HOME` changed
Keychain lookup; an installed PTY initially had zero terminal dimensions; and a
PowerShell download fixture's variable was shadowed by the installer's URL variable.
None required a production fallback, credential migration or relaxed validation.
