## Failures retained

The [first Mac lifecycle](evidence/rc14-cli-2026-10-01/macos-lifecycle.json)
passed live coding/approvals using 9 requests, then stopped at uninstall. The
runner incorrectly counted the untouched ordinary installation's PATH block as
disposable residue. A failing public-runner regression reproduced this coexistence
case; commit `da4b8dd` scopes cleanup assertions to the owned shell tree. The
[recovery check](evidence/rc14-cli-2026-10-01/macos-recovery.json) verified removal
of the retained test Keychain entry. The original failed report is unchanged.
The same rc14 bytes passed the complete rerun above. Total measured Mac requests
including that runner-failure attempt: 25.

Windows fixture preparation initially lacked an installer asset and metadata
snapshot; both missing prerequisites were supplied and failures retained locally.
PowerShell 5 returned an empty completed-child exit code until its native process
handle was retained. Existing ordinary tofa PATH precedence required the documented
session activation for the custom disposable installation. The original account
PATH is restored by native synthetic tests. Native rc14 lifecycle then passed
fresh discovery, repeated install, preserve/reinstall, checksum rejection,
asynchronous helper failure/cancellation/timeout, purge and unrelated-state checks.

The installed Codex Windows fixture initially lacked an explicit sandbox backend.
Selecting the same restricted-token backend used by earlier ARM64 tests made the
missing split-root support visible; narrowing writable roots to the workspace
allowed process creation. Subsequent diagnostics independently showed that the
sandboxed Python process could not read the private test workspace, including with
an explicit working directory and absolute input path. This is a native sandbox
prerequisite failure, not a provider/model result. No live Windows inference was
started and no unsafe sandbox bypass was used.

[OpenAI's Windows sandbox documentation](https://learn.chatgpt.com/docs/windows/windows-sandbox)
recommends elevated setup, which creates dedicated sandbox accounts and firewall/
local-policy boundaries. Maintainer approval was requested before those additional
machine-level changes. That approval is the remaining setup gate.

A native fixture regression also reproduced Unix `printf` failing under Windows
PowerShell. The approval fixture now proposes `Write-Output` on Windows and uses
the same command in its allow/deny prompts. A proxy test verifies the actual
harmless command in the native shell and that its proposal still requires
escalation. This does not substitute for installed-client Guardian acceptance.
A separate proxy assertion now accepts either transport refusal or deadline expiry
for its one-second refused-loopback probe; the request-count and failure-retention
assertions are unchanged.

The Windows guest's original TLS failure was independently reproduced and fixed
with Ethernet IPv4 MTU 1200 in active/persistent settings. Returning to 1500
reproduced failure; 1400 also failed. TLS hostname/certificate verification remains
enabled. This is documented in the [onboarding network evidence](onboarding-74-2026-10-01.md).
Both normal-account installations now resolve to the downloaded rc14 executable;
[Windows restoration evidence](evidence/rc14-cli-2026-10-01/windows-restored.json)
records unchanged ordinary launcher configuration.
